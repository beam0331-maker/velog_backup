<h3 id="1-클라우드-컴퓨팅">1. 클라우드 컴퓨팅</h3>
<h4 id="1-1-개념">1-1. 개념</h4>
<ul>
<li><strong>개념:</strong> 클라우드 컴퓨팅은 IT 리소스(컴퓨팅, 스토리지, 네트워크 등)를 사용한 만큼만 비용을 지불하고 빌려 쓰는 서비스다. 반대로 온프레미스(on-premise)는 사용자가 직접 IT 리소스를 구입하는 방식이다.</li>
</ul>
<h4 id="1-2-종류">1-2. 종류</h4>
<ul>
<li><strong>개념:</strong> 클라우드 서비스는 관리 범위를 얼마나 위임하는지에 따라 &quot;As a Service&quot; 형태로 나뉜다.</li>
</ul>

<td>EC2</td>

<h4 id="1-3-구현-모델">1-3. 구현 모델</h4>
<ul>
<li><strong>퍼블릭 클라우드:</strong> CSP가 운영·관리하고 일반 사용자가 서비스를 받는 형태 (AWS, Google Cloud, MS Azure)</li>
<li><strong>프라이빗 클라우드:</strong> 회사가 자체적으로 클라우드 환경을 구축해 서비스하는 형태</li>
<li><strong>하이브리드 클라우드:</strong> 퍼블릭과 프라이빗을 혼합한 형태</li>
</ul>
<h4 id="1-4-클라우드-장점">1-4. 클라우드 장점</h4>
<ul>
<li>자본비용(IT 리소스 구입 비용)을 가변비용으로 대체한다.</li>
<li>규모의 경제를 통해 가격이 싸진다.</li>
<li>IT 리소스 용량 추정이 필요 없다. (과대·과소 추정 문제 해결)</li>
<li>속도와 대응력이 올라간다.</li>
</ul>
<h4 id="1-5-클라우드-주요-용어">1-5. 클라우드 주요 용어</h4>
<p><strong>가. 고가용성 (High Availability, HA)</strong></p>
<ul>
<li><strong>개념:</strong> 장애가 발생했을 때 이를 해결해 서비스를 계속 운영할 수 있는 능력이다. 빠른 복구가 최종 목표다.</li>
<li><strong>필요 기술:</strong> 이중화(단일 장애 지점 제거), 장애감지(health check), 자동우회(failover), 확장성, 무중단 배포</li>
</ul>
<table>
<thead>
<tr>
<th>배포 방식</th>
<th>특징</th>
</tr>
</thead>
<tbody><tr>
<td><strong>Rolling Update</strong></td>
<td>v2를 만들고 v1을 지우는 과정을 반복해 최종적으로 v2만 남는다</td>
</tr>
<tr>
<td><strong>Blue/Green</strong></td>
<td>2개의 서버가 필요하고 트래픽을 한 번에 전환한다. 금융권에서 주로 쓰인다</td>
</tr>
<tr>
<td><strong>Canary</strong></td>
<td>신규 버전을 일부 사용자에게만 먼저 배포한다</td>
</tr>
</tbody></table>
<blockquote>
<p>원칙만으로는 실무에 적용하기 어렵다. RTO(복구 목표 시간)와 RPO(허용 가능한 데이터 유실 범위)를 숫자로 정의하고, 모든 서비스에 똑같은 HA 수준을 적용하는 대신 서비스 등급(Tier)에 따라 다르게 적용해야 한다.</p>
</blockquote>
<ul>
<li>Tier-1(핵심 서비스): Multi-AZ Active-Active, RTO 1분 이내</li>
<li>Tier-3(내부 도구): Single-AZ, 수동 복구 허용</li>
</ul>
<blockquote>
<p>헬스체크는 &quot;서버가 켜져 있는가&quot;만 확인해서는 안 되고, DB·캐시 같은 하위 의존성 상태까지 포함해야 한다. 하위 의존성 확인이 빠지면 DB 연결이 끊긴 상태에서도 healthy로 잘못 판단해 장애가 전파될 수 있다.</p>
</blockquote>
<p><strong>나. 장애내구성 / 내결함성 (Fault Tolerance) — 다층 방어 체계</strong></p>
<ul>
<li><strong>개념:</strong> 고가용성과 겹치는 부분이 있지만 한 단계 강화된 개념이다. 장애가 발생해도 무중단으로 서비스를 계속 운영하는 것이 목표다.</li>
<li><strong>핵심 원칙:</strong> 단일 계층의 방어(예: 차단만 하기)로는 부족하고, <strong>차단 → 대체 응답 → 데이터 보호</strong>의 세 단계 방어가 함께 작동해야 무중단 서비스가 가능하다.</li>
</ul>

<p><strong>레벨 1: Circuit Breaker — 장애 격리</strong></p>
<ul>
<li><strong>역할:</strong> 의존하는 외부 서비스의 실패를 감지하고 요청을 즉시 차단해 장애를 격리한다.</li>
</ul>

</tr>
<tr>
<td><strong>OPEN</strong> (차단)</td>
<td>요청을 차단하고 즉시 실패 응답 반환</td>

<tr>

<td>일부 요청만 흘려보내 정상화 여부 확인</td>
</tr>
</tbody></table>
<blockquote>
<p>Circuit Breaker는 외부 서비스 장애가 내 시스템으로 전파되는 것을 방지하는 첫 번째 방어선이다.</p>
</blockquote>

<ul>
<li><strong>역할:</strong> Circuit Breaker가 요청을 차단했을 때, 사용자에게 제공할 대체 응답을 설계한다.</li>

<p><strong>다. 확장성(Scalability) / 탄력성(Elasticity)</strong></p>
<ul>
<li><strong>개념:</strong> 트래픽 증감에 따라 자원을 늘리고 줄이는 능력이다.</li>
<li><strong>탄력성 설계조건:</strong> stateless, fast startup, automation, monitoring</li>
</ul>
<blockquote>
<p>서버가 상태를 저장하면 안 된다는 <code>stateless 원칙</code>은 Auto Scaling으로 신규 인스턴스가 생기는 순간 세션 정합성이 깨지는 문제를 막기 위한 전제조건이다. 세션 데이터를 Redis 같은 외부 저장소로 분리하는 것이 실무 표준이다.</p>
</blockquote>
<ul>
<li><strong>CPU 70% 스케일 아웃 기준:</strong> 임의의 숫자가 아니다. 스케일 아웃이 완료될 때까지 걸리는 시간(Warm-up) 동안 기존 자원으로 버틸 수 있는 안전 마진을 확보하기 위한 기준이다. 너무 낮게(예: 50%) 잡으면 플래핑으로 비용이 낭비되고, 너무 높게 잡으면 대응이 늦어 장애로 이어진다.</li>
<li><strong>쿨다운(Cool-down):</strong> 스케일 아웃/인 직후 일정 시간 추가 판단을 하지 않는다. 스케일 인 쿨다운은 스케일 아웃 쿨다운보다 보수적으로(더 길게) 설정하는 것이 표준이다.</li>
<li><strong>최소 용량(Minimum Capacity):</strong> 평균 트래픽이 아닌 예상 피크치(과거 관측된 최대 동시 접속자 수·초당 요청 수 등) 기준으로 설정한다. 평균치로 설정하면 예측 가능한 피크 상황에서 스케일링이 완료되기 전까지 공백 구간이 생겨 장애로 이어질 수 있다.</li>
</ul>

<li><strong>개념:</strong> 필요한 IT 리소스를 준비하고 할당하는 과정이다.</li>
</ul>

<h3 id="2-aws-클라우드-기초">2. AWS 클라우드 기초</h3>
<h4 id="2-1-aws-구조">2-1. AWS 구조</h4>
<ul>
<li><strong>계층:</strong> AWS Account → Region → Availability Zone(AZ) → Data Center</li>
</ul>
<h4 id="2-2-리전-region">2-2. 리전 (Region)</h4>
<p>리전은 AWS 서비스가 제공되는 서버의 물리적 위치를 의미한다. 이것은 실무에서 아주 중요한 설계 결정이 되는 개념이다.</p>
<ul>
<li><strong>서울 리전:</strong> ap-northeast-2</li>
<li><strong>버지니아 리전:</strong> us-east-1 — 글로벌 서비스의 기준 리전이다</li>
</ul>
<p>버지니아 리전이 빌링, CloudFront, IAM, Route53 같은 글로벌 서비스의 기준 리전인 이유는, 이들 서비스가 전 세계 인프라가 데이터를 공유하는 구조이기 때문이다.</p>
<blockquote>
<p>리전 선정 4대 기준(지연속도/사용 가능한 서비스/비용/법적 요구사항)에는 실무에서 우선순위가 필요하다. <code>법적 요구사항</code>은 위반 시 서비스 중단 이상의 법적 리스크를 초래하므로 비용·성능보다 항상 우선한다.</p>
</blockquote>
<h4 id="2-3-가용영역-availability-zone-az">2-3. 가용영역 (Availability Zone, AZ)</h4>
<ul>

<h3 id="🔥-오늘의-딥다이브-회고">🔥 오늘의 딥다이브 (회고)</h3>
<h4 id="1-circuit-breaker와-fallback-설계--장애-대응의-온전한-구조">1. Circuit Breaker와 Fallback 설계 — 장애 대응의 온전한 구조</h4>
<p>Circuit Breaker는 단순히 &quot;장애 감지 후 격리 기술&quot;이 아니라 &quot;차단 이후 사용자에게 정상적이 서비스로 느끼게 설계 할것&quot;이 핵심인 문제였다.</p>
<ul>
<li><p><strong>상태 전이의 의미</strong>: CLOSED → OPEN → HALF-OPEN의 세 상태는 단순한 on/off가 아니라 장애 상황을 점진적으로 대응하는 단계적 절차를 포함한다. 특히 HALF-OPEN 상태에서 &quot;얼마나 많은 요청을 시험할 것인가&quot;는 서비스의 장애 복구 속도에 큰 영향을 미친다.</p>
</li>
<li><p><strong>Fallback 전략의 사전 정의</strong>: Circuit Breaker가 OPEN되면 캐시 응답, 기본값, 큐 적재, 명시적 에러 중 어느 것을 선택할지는 &quot;장애가 터진 순간에 결정할 수 없다&quot;는 게 핵심이다. 캐시 응답을 선택하면 사용자가 오래된 데이터를 보는 것이므로, &quot;최종 갱신 시각&quot; 메타데이터를 반드시 함께 반환해야 신뢰도를 확보할 수 있다. 이런 세부사항까지 설계 단계에서 정해져야 실제 장애 상황에서 당황하지 않는다.</p>
</li>
<li><p><strong>주의점</strong>: Fallback을 무조건 많이 만드는 것이 답이 아니다. 각 서비스별로 가장 적절한 Fallback 1~2개를 명확히 선택하고, 나머지는 비상용으로만 두는 것이 운영 부담을 줄인다.</p>
</li>
</ul>
<h4 id="2-auto-scaling-임계치-70의-근거">2. Auto Scaling 임계치 70%의 근거</h4>
<p>&quot;왜 하필 CPU 70%인가?&quot;라는 질문에서 출발했는데, 이게 단순한 관행 보다는 물리적·기술적 근거가 있다는 걸 알았다.</p>
<ul>
<li><p><strong>Warm-up 시간과의 관계</strong>: 신규 인스턴스를 만들어서 트래픽을 받을 때까지 걸리는 시간(컨테이너 이미지 pull, 애플리케이션 초기화, 헬스체크 통과 등)은 보통 30초~수 분이다. 이 시간 동안 기존 인스턴스는 CPU를 써야 하므로, 70%는 &quot;나머지 30%의 여유로 이 기간을 버틸 수 있는 수준&quot;을 뜻한다.</p>
</li>
<li><p><strong>플래핑 방지</strong>: 임계치가 너무 낮으면(예: 50%) 트래픽 스파이크가 있을 때마다 스케일링이 발동하고, 새 인스턴스가 뜨면 CPU가 떨어져서 다시 줄어드는 악순환(플래핑)이 생긴다. 이는 비용 낭비뿐 아니라 시스템 불안정성을 초래한다.</p>
</li>
<li><p><strong>주의점</strong>: 70%는 &quot;정답&quot;이 아니라 &quot;검증된 출발점&quot;이다. 실제 서비스의 부하 테스트 결과에 따라 60~80% 범위 내에서 조정하는 것이 실무 표준이며, CPU 외에 메모리, 네트워크 대역폭, DB 커넥션 풀 같은 다른 지표와 복합적으로 판단해야 한다.</p>
</li>
</ul>
<h4 id="3-rpo-트레이드오프-이해하기--rds-multi-az-vs-dynamodb-global-tables">3. RPO 트레이드오프 이해하기 — RDS Multi-AZ vs DynamoDB Global Tables</h4>
<p>&quot;RPO=0이면 무조건 좋은 거 아닌가?&quot;라는 질문을 던졌을 때, 이게 &quot;무손실&quot;이라는 이점과 &quot;지연시간&quot;이라는 비용을 동시에 갖고 있다는 걸 정확히 짚을 수 있었다.</p>
<ul>
<li><p><strong>동기 복제의 비용</strong>: RPO=0을 달성하려면 쓰기 트랜잭션이 모든 복제본에 반영될 때까지 응답을 기다려야 한다. 이는 네트워크 왕복 시간(round-trip time)을 계속 더하는 것이므로 단일 AZ 쓰기보다 지연시간이 눈에 띨 정도로 늘어난다.</p>
</li>
<li><p><strong>RDS vs DynamoDB의 구분</strong>: 둘 다 다중화 복제를 지원하지만, RDS Multi-AZ는 같은 리전 내 다른 AZ로 동기 복제해서 AZ 장애만 대비하는 HA 도구인 반면, DynamoDB Global Tables는 리전 간 비동기 복제로 리전 전체 장애와 전 세계 사용자의 지연시간을 동시에 해결하는 글로벌 분산 도구다. 이들은 대체재가 아니라 &quot;적용하는 계층이 다른&quot; 도구라는 구분이 핵심이다.</p>
</li>
<li><p><strong>주의점</strong>: 비용이 들기 때문에 무조건 Multi-AZ를 쓰는 게 아니라, 서비스 Tier에 따라 RPO를 다르게 적용해야 한다. 결제·거래 같은 금융 데이터는 RPO=0, 로그나 통계 데이터는 RPO 수 초 수용 가능한 식으로 판단해야 실무에서 비용을 관리할 수 있다.</p>
</li>
</ul>
