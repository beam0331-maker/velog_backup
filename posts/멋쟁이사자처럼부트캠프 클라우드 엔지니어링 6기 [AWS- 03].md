<h1 id="aws-auto-scaling-및-application-load-balanceralb-구축-실습">AWS Auto Scaling 및 Application Load Balancer(ALB) 구축 실습</h1>
<h2 id="1-auto-scaling의-개념-및-핵심-구성-요소">1. Auto Scaling의 개념 및 핵심 구성 요소</h2>
<ul>
<li><strong>Auto Scaling의 정의 및 목적</strong><ul>
<li>시스템의 트래픽 부하 변동에 따라 컴퓨팅 자원(EC2 인스턴스)의 개수를 자동으로 확장(Scale-out)하거나 축소(Scale-in)하는 기술이다.</li>
<li>가용성을 보장(High Availability)하는 동시에, 불필요한 자원 낭비를 방지하여 비용을 최적화하고 안정적인 성능을 유지하는 데 목적이 있다.</li>
</ul>
</li>
<li><strong>시작 템플릿(Launch Template)</strong><ul>
<li>오토 스케일링 그룹이 새로운 EC2 인스턴스를 확장할 때 사용할 서버의 설계도 스펙을 정의한다.</li>
<li>구성 항목으로 AMI(운영체제 이미지), 인스턴스 유형(CPU/Memory), 보안 그룹, 키 페어, 그리고 초기 부팅 시 자동 실행될 사용자 데이터(User Data) 스크립트 등이 있다.</li>
</ul>
</li>
<li><strong>Auto Scaling Group (ASG)</strong><ul>
<li>가상 서버 인스턴스들을 하나의 논리적 관리 대상으로 묶어 개수 유지 및 장애 대처를 담당하는 최소 단위이다.</li>
<li>그룹 운영의 핵심 제어 변수로 최소 용량(Min), 원하는 용량(Desired, 초기 용량), 최대 용량(Max)을 설정하여 인스턴스의 스케일링을 관리한다.</li>
</ul>
</li>
<li><strong>CloudWatch 및 Metric 기반 스케일링</strong><ul>
<li>AWS의 모니터링 시스템으로, 오토 스케일링 그룹의 CPU 사용량 등의 가용한 성능 지표(Metric)를 수집하여 자원의 확장 및 축소 여부를 판단하는 임계치 근거를 제공한다.</li>
</ul>
</li>
</ul>
<h2 id="2-elbelastic-load-balancer">2. ELB(Elastic Load Balancer)</h2>
<ul>
<li><strong>ALB(Application Load Balancer)의 특징</strong><ul>
<li>OSI 7계층 중 애플리케이션 계층에서 동작하는 전용 로드밸런서로, HTTP 및 HTTPS 프로토콜 기반의 웹 서비스 트래픽 처리에 최적화되어 있다.</li>
<li>URL 경로, HTTP 헤더, 메소드, 쿼리 스트링 등 상위 레이어의 패킷 데이터를 분석하여 세부적인 라우팅 규칙(Rule)을 적용할 수 있다.</li>
</ul>
</li>
<li><strong>대상 그룹(Target Group)과 리스너(Listener)</strong><ul>
<li><strong>대상 그룹:</strong> 로드밸런서가 트래픽을 최종적으로 라우팅하여 전달할 실제 컴퓨팅 자원(Instance, IP 등)의 집합 체계이다.</li>
<li><strong>리스너:</strong> 프로토콜과 포트(예: HTTP 80) 설정을 기반으로 외부 연결 요청을 대기하고 수신하는 주체이며, 등록된 규칙에 따라 대상 그룹으로 트래픽을 전달(Forward)한다.</li>
</ul>
</li>
<li><strong>상태 검사(Health Check) 메커니즘</strong><ul>
<li>로드밸런서가 주기적으로 각 인스턴스의 특정 포트에 프로브(Probe) 패킷을 보내 서버의 정상 여부를 확인하는 기능이다.</li>
<li>장애가 발생한 비정상(Unhealthy) 인스턴스를 감지하면 즉시 트래픽 할당 대상에서 제외하고, 오토 스케일링 그룹과 연동 시 해당 인스턴스를 폐기한 후 정상 인스턴스를 재구동하는 자가 치유(Self-healing) 기반을 제공한다.</li>
</ul>
</li>
</ul>
<h2 id="3-실습-시작-템플릿launch-template-작성-규칙">3. [실습] 시작 템플릿(Launch Template) 작성 규칙</h2>
<p><img alt="" src="https://velog.velcdn.com/images/beam0331/post/289cb8af-530e-4749-a462-532d368a6c73/image.png" /></p>
<p><img alt="" src="https://velog.velcdn.com/images/beam0331/post/4d548ed2-c6ac-4ad5-b0ef-30ee07eb60c5/image.png" /></p>
<ul>
<li><strong>인스턴스 스펙 지정 및 네트워크 제약</strong><ul>
<li>시작 템플릿 이름: <code>demo-my-ec2-template</code></li>
<li>AMI: Ubuntu Server 24.04 LTS 원본 이미지를 지정하고, 가벼운 컴퓨팅 테스트를 위해 프리티어 사양인 <code>t3.micro</code> 인스턴스 유형을 매핑한다.</li>
<li>유연한 수평 확장을 위해 시작 템플릿 내부의 네트워크 설정 단계에서는 특정 서브넷 and 가용 영역을 지정하지 않고 공란 처리한다.</li>
</ul>
</li>
<li><strong>가상 방화벽(보안 그룹) 및 광역 허용 규칙 구성</strong><ul>
<li>신규 보안 그룹인 <code>demo-my-security-group</code>을 정의한다.</li>
<li>인바운드 규칙으로 실습 목적상의 트래픽 유입 테스트를 위해 HTTP 프로토콜 전체 및 모든 소스 주소 대역(<code>0.0.0.0/0</code>)에 대해 개방 설정을 적용한다.</li>
</ul>
</li>
<li><strong>사용자 데이터(User Data) 스크립트를 통한 아파치 웹 서버 자동화</strong><pre><code class="language-shell">#!/bin/bash
apt update -y
apt install apache2 -y
systemctl start apache2
systemctl enable apache2
echo &quot;&lt;h1&gt;Hello $(hostname -f)&lt;/h1&gt;&quot; &gt; /var/www/html/index.html</code></pre>
</li>
</ul>
<h2 id="4-실습-auto-scaling-group-생성-및-관리화-프로세스">4. [실습] Auto Scaling Group 생성 및 관리화 프로세스</h2>
<p><img alt="" src="https://velog.velcdn.com/images/beam0331/post/f3857972-2a02-472b-854b-791f986f2bcc/image.png" /></p>
<ul>
<li><strong>기본 VPC 매핑 및 다중 가용 영역(Multi-AZ) 바인딩</strong><ul>
<li>그룹 이름: <code>demo-my-auto-scaling-group</code></li>
<li>template 에서 선택한 VPC와 같은 VPC를 선택하고, 특정 물리 데이터 센터 장애에 대응하여 고가용성을 확보할 수 있도록 <code>가용 영역 및 서브넷</code>을 복수 선택하여 분산 배치 환경을 선언한다.</li>
<li>VPC를 임의로 설계 할 수 있다는 것을 보이기 위해 커스텀 VPC를 사용했다.</li>
</ul>
</li>
</ul>
<p><img alt="" src="https://velog.velcdn.com/images/beam0331/post/c804d38f-a539-4b7c-9864-959afa59f92c/image.png" /></p>
<ul>
<li><strong>자원 용량 설계(Capacity 설정)</strong><ul>
<li>초기 부팅 시 필요한 목표 용량(Desired Capacity)을 <code>3</code>으로 선언하고, 최소 용량 <code>1</code>, 최대 용량 <code>3</code>으로 임계치를 바인딩하여 오토 스케일링 그룹 활성화와 동시에 3대의 EC2 인스턴스가 독립적으로 배치 구동되도록 제어한다.</li>
</ul>
</li>
<li><strong>인스턴스 인서비스(InService) 및 가용성 검증</strong><ul>
<li>오토 스케일링 그룹의 인스턴스 관리 탭을 확인하여 고유 인스턴스 ID를 가진 3대의 노드가 <code>InService</code> 상태 및 <code>Healthy</code> 등급으로 정상 작동하는지 모니터링한다.</li>
<li>각 가상 서버의 개별 퍼블릭 IP 주소로 브라우저 접근을 시도하여, 사용자 데이터 스크립트로 구성한 가상 웹 페이지가 정상 응답 신호를 반환하는지 대조 검증한다.</li>
</ul>
</li>
</ul>
<h2 id="5-실습-alb-연동-및-로드밸런서-유입-트래픽-제어-보안-그룹-라우팅">5. [실습] ALB 연동 및 로드밸런서 유입 트래픽 제어 (보안 그룹 라우팅)</h2>
<h3 id="5-1-대상-그룹target-group-생성-및-인스턴스-등록">5-1. 대상 그룹(Target Group) 생성 및 인스턴스 등록</h3>
<ol>
<li><strong>대상 그룹 생성 메뉴 진입</strong><ul>
<li>EC2 대시보드 좌측 메뉴에서 <code>로드 밸런싱</code> -&gt; <code>대상 그룹(Target Groups)</code>을 선택하고 <code>대상 그룹 생성(Create target group)</code>을 클릭한다.</li>
</ul>
</li>
<li><strong>기본 구성 설정</strong><ul>
<li><strong>대상 유형 선택(Target type):</strong> 오토 스케일링 그룹의 가상 서버들을 묶어 관리해야 하므로 <strong>인스턴스(Instances)</strong>를 선택한다.</li>
<li><strong>대상 그룹 이름(Target group name):</strong> <code>demo-my-tg-alb</code>를 입력한다.</li>
<li><strong>프로토콜 및 포트:</strong> 아파치 웹서버 통신 규격에 맞춰 <strong>HTTP / 80</strong> 포트로 지정한다.</li>
<li><strong>VPC:</strong> 시작 템플릿 및 오토 스케일링 그룹에서 지정한 것과 동일한 <strong>VPC</strong>를 선택한다.</li>
</ul>
</li>
<li><strong>상태 검사(Health check) 설정</strong><ul>
<li>프로토콜은 <code>HTTP</code>, 상태 검사 경로는 루트 디렉토리인 <code>/</code> 기본값을 유지한다. 아파치 서버가 정상 구동 중이면 <code>200 OK</code> 사인을 받아 정상 상태로 인식한다.</li>
</ul>
</li>
<li><strong>대상 등록 (Register targets)</strong><ul>
<li>하단의 가용한 인스턴스 목록에서 오토 스케일링 그룹이 자동으로 생성한 3대의 EC2 인스턴스를 모두 체크하여 선택한다.</li>
<li><code>아래에 보류 중인 것으로 포함(Include as pending below)</code> 버튼을 클릭하여 대상 그룹의 포워딩 타겟 리스트에 등록한 후, <code>대상 그룹 생성</code>을 눌러 완료한다.</li>
</ul>
</li>
</ol>
<h3 id="5-2-application-load-balanceralb-생성-및-네트워크-맵핑">5-2. Application Load Balancer(ALB) 생성 및 네트워크 맵핑</h3>
<ol>
<li><strong>로드 밸런서 생성 메뉴 진입</strong><ul>
<li>EC2 대시보드 좌측 메뉴에서 <code>로드 밸런서(Load Balancers)</code>를 선택하고 <code>로드 밸런서 생성</code> 버튼을 클릭한다.</li>
<li>제공되는 4가지 타입 중 <strong>Application Load Balancer</strong>의 <code>생성</code> 버튼을 클릭한다.</li>
</ul>
</li>
<li><strong>기본 구성 설정</strong><ul>
<li><strong>로드 밸런서 이름(Load balancer name):</strong> <code>demo-my-alb</code>를 입력한다.</li>
<li><strong>체계(Scheme):</strong> 외부 공인 인터넷망의 클라이언트 요청을 수신하여 포워딩해야 하므로 <strong>인터넷 지향(Internet-facing)</strong>을 선택한다.</li>
<li><strong>IP 주소 유형:</strong> <code>IPv4</code>를 유지한다.</li>
</ul>
</li>
<li><strong>네트워크 매핑 (Network mapping)</strong><ul>
<li><strong>VPC:</strong> 앞서 설정한 <strong>VPC</strong>를 바인딩한다.</li>
<li><strong>매핑(Mappings):</strong> 다중 가용 영역(Multi-AZ) 부하 분산과 가용성 확보를 위해, 해당 리전 내에 가용한 모든 가용 영역(AZ)과 서브넷 코드를 복수 선택하여 체크한다.</li>
</ul>
</li>
<li><strong>보안 그룹(Security groups) 지정</strong><ul>
<li>로드밸런서 자체의 패킷 진입을 통제할 전용 가상 방화벽 규칙 생성을 위해 <code>새 보안 그룹 생성</code> 링크를 클릭한다.</li>
<li>보안 그룹 이름은 <code>demo-my-sg-alb</code>로 지정하고, 인바운드 규칙에 <strong>HTTP (80 포트)</strong> / 소스 주소 대역 광역 허용(<strong><code>0.0.0.0/0</code></strong>)을 추가한 뒤 저장한다.</li>
<li>다시 로드밸런서 생성 화면으로 돌아와 기존 기본 보안 그룹을 제거하고, 방금 생성한 <code>demo-my-sg-alb</code>를 배정한다.</li>
</ul>
</li>
<li><strong>리스너 및 라우팅 (Listeners and routing)</strong><ul>
<li>외부 트래픽을 수신할 기본 리스너 설정을 <strong>프로토콜 HTTP / 포트 80</strong>으로 지정한다.</li>
<li><strong>작업(Default action):</strong> <code>전달(Forward to)</code>을 선택하고, 방금 전 생성해 둔 대상 그룹인 <code>demo-my-tg-alb</code>를 드롭다운 메뉴에서 링킹한다.</li>
</ul>
</li>
<li><strong>최종 생성</strong><ul>
<li>설정을 최종 검토한 뒤 하단의 <code>로드 밸런서 생성</code>을 클릭한다. 상태 필드가 <code>Pending</code>에서 <code>활성(Active)</code>으로 전환될 때까지 대기한다.</li>
</ul>
</li>
</ol>
<h3 id="5-3-보안-그룹을-통한-ec2-유입-제어-alb-전용-허용">5-3. 보안 그룹을 통한 EC2 유입 제어 (ALB 전용 허용)</h3>
<ol>
<li><strong>문제점</strong><ul>
<li>현재 상태에서는 EC2 인스턴스의 보안 그룹 인바운드가 <code>0.0.0.0/0</code>으로 개방되어 있어, 로드밸런서를 거치지 않고 각 인스턴스의 퍼블릭 IP로 직접 우회 접속이 가능하다. </li>
</ul>
</li>
<li><strong>인스턴스 보안 그룹 수정</strong><ul>
<li>EC2 서비스 메뉴의 <code>보안 그룹</code>으로 이동하여 인스턴스 전용 보안 그룹(<code>demo-my-security-group</code>)을 선택하고 <code>인바운드 규칙 편집</code>을 클릭한다.</li>
<li>기존에 설정되어 있던 HTTP / <code>0.0.0.0/0</code> 허용 규칙을 삭제한다.</li>
</ul>
</li>
<li><strong>인바운드 규칙 추가 (라우팅 차단)</strong><ul>
<li>*<em>유형: *</em><code>HTTP (80번 포트)</code>로 지정한다.</li>
<li><strong>소스: *<em><code>사용자 지정</code> 선택, 주소창에 IP 대신 *</em>ALB의 전용 보안 그룹 ID(<code>demo-my-sg-alb</code>)</strong>를 검색하여 입력·선택한다.</li>
<li>EC2 인스턴스는 오직 로드밸런서에서 오는 데이터 패킷만 내부로 수신 허가하고, 직접적인 퍼블릭 외부 접근은 차단하는 격리 환경을 구축하게 된다.</li>
</ul>
</li>
</ol>
<h3 id="5-4-엔드포인트-검증">5-4. 엔드포인트 검증</h3>
<ol>
<li><strong>로드밸런서 주소 접속 테스트</strong><ul>
<li>AWS 콘솔에서 발급된 ALB 고유의 <strong>DNS 이름</strong>(예: <code>demo-my-alb-xxxx.ap-northeast-2.elb.amazonaws.com</code>) 주소를 복사하여 브라우저에 입력하고 호출한다.</li>

</ul>
</li>
<li><strong>직접 우회 접근 차단 검증</strong><ul>
<li>오토 스케일링 그룹 내부 개별 인스턴스의 상세 정보 탭에 명시된 퍼블릭 IP 주소를 주소창에 직접 입력하여 웹 접속을 시도한다.</li>
<li>라우팅 제한 보안 그룹 설정이 정상 작동하여 커널단에서 패킷을 차단시키므로, 접속이 이루어지지 않고 타임아웃(Connection Timeout)이 발생하는지 최종 교차 검증한다.</li>
</ul>
</li>
</ol>

<h3 id="1-문제-정의">1. 문제 정의</h3>
<p>Auto Scaling 그룹을 통해 동적으로 생성되는 EC2 인스턴스에 <strong>퍼블릭 IP가 할당되지 않아, 외부에서 해당 인스턴스로 직접 접속할 수 없는 문제</strong>가 발생.</p>
<ul>
<li><strong>현상:</strong> 오토 스케일링으로 새로 생성된 EC2 인스턴스의 인스턴스 상세 정보에 퍼블릭 IPv4 주소 항목이 비어 있음</li>
<li><strong>영향:</strong> 외부 사용자가 도메인 또는 IP 주소로 서비스에 접속할 수 없음</li>
</ul>
<hr />
<h3 id="2-원인-분석-root-cause-analysis">2. 원인 분석 (Root Cause Analysis)</h3>
<p>이미 생성된 EC2 인스턴스에 사후적으로 퍼블릭 IP를 붙일 수 없는 근본 원인은 다음 두 가지로 압축된다.</p>
<h4 id="21-aws-네트워크-인터페이스eni의-생명주기-한계">2.1 AWS 네트워크 인터페이스(ENI)의 생명주기 한계</h4>
<p>EC2 인스턴스 생성 시점에 주 네트워크 인터페이스(Primary ENI, eth0)가 서브넷 내부에서 함께 생성되며, <strong>인스턴스 생성 시점에 퍼블릭 IP를 할당받지 못한 Primary ENI는 사후에 동적 퍼블릭 IPv4 주소를 추가로 부여받을 수 없다.</strong> 즉, &quot;퍼블릭 IP 자동 할당&quot; 설정이 꺼진 서브넷에서 이미 생성된 인스턴스는, 차후 설정이 불가능하다.</p>
<blockquote>
<p>📝 <strong>[용어 설명] Primary ENI란?</strong>
ENI(Elastic Network Interface)는 EC2 인스턴스에 부착되는 가상 네트워크 카드, 프라이빗/퍼블릭 IP, MAC 주소, 보안 그룹 정보를 가지고 있다. 그중 <strong>Primary ENI</strong>는 인스턴스가 생성될 때 자동으로 함께 새성되며 절대 분리할 수 없는 '기본 네트워크 인터페이스(주로 eth0)'이다. 추가 ENI(Secondary ENI)를 더 붙이는 것은 가능하지만, <strong>Primary ENI의 퍼블릭 IP 할당 여부는 인스턴스 생성 시점에 고정</strong>되어 이후 변경할 수 없다는 점이 이번 문제의 핵심.</p>
</blockquote>
<h4 id="22-불변-인프라immutable-infrastructure-패러다임">2.2 불변 인프라(Immutable Infrastructure) 패러다임</h4>
<p>클라우드 아키텍처는 실행 중인 서버의 설정을 직접 바꾸지 않고, <strong>&quot;문제가 있으면 기존 서버를 폐기하고 새 서버를 띄운다&quot;</strong>는 불변 인프라 원칙을 따른다. ASG 역시 이 원칙 위에서 동작하기 때문에, 구동 중인 EC2의 네트워크 속성(퍼블릭 IP 할당 여부 포함)을 사후에 바꾸는 옵션 자체가 기본적으로 제공되지 않는다.</p>
<blockquote>
<p>📝 <strong>[정리]</strong> 결국 2.1과 2.2는 같은 결론으로 수렴합니다. *&quot;이미 떠 있는 인스턴스는 못 고친다 → 고치려면 새로 띄워야 한다.&quot;* 이 전제가 3장의 해결 방법 두 가지가 왜 그런 절차를 취하는지를 결정합니다.</p>
</blockquote>
<hr />
<h3 id="3-해결-방법-solutions">3. 해결 방법 (Solutions)</h3>
<p>문제의 원인이 &quot;생성 시점에 고정되는 Primary ENI&quot;에 있으므로, 해결 방법은 결국 <strong>새 설정으로 인스턴스를 다시 만드는 방법</strong>이 유일하다</p>
<h4 id="31-시작-템플릿-수정--인스턴스-새로고침">3.1 시작 템플릿 수정 + 인스턴스 새로고침</h4>
<p><strong>개념:</strong> 시작 템플릿에서 '퍼블릭 IP 자동 할당'을 활성화한 새 버전을 만들고, ASG의 인스턴스 새로고침 기능으로 기존 인스턴스를 점진적으로 교체하여 신규 인스턴스가 생성 시점부터 퍼블릭 IP를 갖도록 한다.</p>
<p><strong>절차:</strong></p>
<ol>
<li>시작 템플릿에서 <strong>새 버전(New Version)</strong>을 생성하고 네트워크 설정에서 '퍼블릭 IPv4 자동 할당'을 활성화</li>
<li>ASG의 시작 템플릿 버전을 최신 버전으로 지정</li>
<li>ASG에서 <strong>인스턴스 새로고침(Instance Refresh)</strong> 실행 → 기존 인스턴스를 순차적으로 종료하고 신규 템플릿 기반 인스턴스로 교체</li>
</ol>
<p><strong>검증 (엔드포인트 확인):</strong></p>
<ol>
<li><strong>신규 인스턴스 퍼블릭 IP 확인:</strong> 인스턴스 새로고침이 완료된 후, ASG 내 인스턴스 목록에서 각 인스턴스의 상세 정보 탭을 열어 퍼블릭 IPv4 주소 확인.</li>
<li><strong>접속 검증:</strong> 새로 부여된 퍼블릭 IP를 주소창에 입력하여 웹 접속 후, 정상 응답이 돌아오는지 확인한다.</li>
</ol>
<blockquote>
<p>📝 <strong>[특징]</strong> 인스턴스 새로고침은 기존 인스턴스를 한 번에 내리지 않고 순차 교체하기 때문에, 교체 대상 인스턴스 수만큼 <strong>쿨다운(Cooldown)/웜업(Warm-up) 대기 시간</strong>이 누적되어 전체 전환에 수 분~수십 분이 소요될 수 있습니다.</p>
</blockquote>
<hr />
<h3 id="4-회고-lessons-learned">4. 회고 (Lessons Learned)</h3>
<ul>
<li>인스턴스가 이미 생성된 이후에는 퍼블릭 IP를 사후적으로 재할당할 방법이 없고, 결국 시작 템플릿을 고친 뒤 인스턴스를 새로 띄우는 절차를 거쳐야 했다.</li>
<li>이 과정에서 <strong>기존 인스턴스 종료 → 신규 인스턴스 부팅 → User Data 초기 설정 → 쿨다운/웜업 대기</strong>까지 이어지는 재설정 과정에 예상보다 많은 시간이 소요되었다.</li>
<li>향후에는 시작 템플릿 단계에서부터 '퍼블릭 IP 자동 할당' 여부를 미리 점검하여, 이미 떠 있는 인스턴스를 뒤늦게 손보는 대신 애초에 올바른 설정으로 생성되도록 하는 것이 재작업 시간을 줄이는 핵심임을 확인.</li>
</ul>
